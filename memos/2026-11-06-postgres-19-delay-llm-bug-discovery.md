- ## Postgres 19 is late because LLMs find bugs faster than humans can fix them
	- **Source**: Robert Haas (Sr. Staff Software Engineer at Databricks; PostgreSQL major contributor and committer), blog post "Postgres 19 is late, and it's AI's fault," Oct 30, 2026. Commit counts are his. Percentages are computed from them. Related: [[2026-05-28-michael-burry-sw50-part2-productivity-cybersecurity]] (Anthropic's Mythos/Glasswing vulnerability hardening), [[2026-10-28-databricks-ali-ghodsi-future-of-firm]] (Lakebase / Neon Postgres), [[2026-09-13-casey-muratori-performance-games-engines-as-ai-preview]], [[2026-03-28-stack-overflow-professional-developers-database-popularity-2024-2025]].
	- **Thesis**: AI has changed how bugs get found much more than how they get fixed. LLMs now find defects that 40 years of human review missed, while fixes still need human review and committing, and the number of reviewers hasn't grown. The result is a **review and maintenance bottleneck**: release dates slip, features get pulled late, and maintainers' time shifts from building new features to fixing old code. Haas's open question is the important one: "how are we ever going to catch up, and how will PostgreSQL continue to innovate?"
- ## The data
	- | Commits, Apr 8 → Sep 25 | 2025 | 2026 | Change |
	  |---|---|---|---|
	  | Master branch | 1,037 | 1,443 | +39% |
	  | Release branch in progress (REL_18 → REL_19_STABLE) | 724 | 1,169 | **+61%** |
	  | Master-only (master minus release branch, approximate) | ~313 | ~274 | **−12%** |
	  | Back-patched to the prior release (REL_17 → REL_18_STABLE) | 248 | 433 | **+75%** |
	- **How to read it**: new work landing only on master actually fell, while fixes back-patched to released code jumped 61–75% in one year. Committers weren't careless. Haas thinks they were about as conservative as in prior years, but LLM users across the internet found far more of their mistakes, and old ones too.
	- **Release slip**: for a decade, major releases have shipped between mid-September and mid-October. PG19 will probably ship in November, and a further postponement is "not impossible."
	- **Late reverts**: three large features were pulled between Aug 27 and Sep 15, long after the Apr 8 feature freeze: **UPDATE/DELETE FOR PORTION OF**, **SQL/PGQ property graph queries**, and **ALTER TABLE … MERGE/SPLIT PARTITION**. Several major features being reverted that late is unusual.
- ## Why it happens
	- **Fixes still need humans**: "LLMs can draft fixes, but those fixes aren't always correct or compliant with PostgreSQL standards," and the reviewers "have not gotten any smarter between 2025 and 2026."
	- **Time spent on bugs isn't spent on review**: committer time went to security issues and back-branch bugs instead of reviewing what was going into v19. Spotting what needed reverting took longer, which caused both the late reverts and the delay.
	- **Discovery got cheaper, but the stock of bugs is the same**: the code base has forty years of accumulated bugs that humans couldn't find and LLMs can. Haas doesn't see this as a sign of poor code quality (Postgres is "some of the cleanest and highest-quality code" he has worked on). Messier code would produce even more findings.
- ## What it means beyond Postgres
	- **Every mature code base faces the same backlog**: if one of the most carefully reviewed open-source projects is swamped, older commercial and open-source software (OS kernels, browsers, databases, enterprise apps) holds a much larger stock of findable bugs. "Every feature that we write… will be scrutinized by AI, and things that would have escaped forever unnoticed… will now be found, perhaps in a matter of hours."
	- **Attackers get the same tools.** The scramble to fix back-branch security bugs is the defensive side of AI vulnerability discovery. Labs giving frontier models to infrastructure owners for hardening (Anthropic's Glasswing, in the Burry memo) are responding to the same imbalance. Demand for patching, vulnerability management and automated remediation tools should rise with it. The cybersecurity products that benefit are the ones that help **fix** bugs, not just find them.
	- **Feature development slows as maintenance absorbs reviewer time.** This is a real cost hidden inside the AI-productivity story: AI makes writing and analyzing code faster, but each verified change still needs a human reviewer. Measured in shipped, reviewed features, output can fall even as commit counts rise. That matches the review-bottleneck theme in AI coding generally.
	- **Effect on managed-Postgres vendors**: Postgres is the most-used database among professional developers (58% in Stack Overflow 2025). Databricks (Lakebase/Neon), AWS (RDS/Aurora), Microsoft (Azure Postgres), Google (AlloyDB), Snowflake (Crunchy Data) and Supabase all build on it. A higher patch rate raises maintenance costs for every fork and managed service. It also favors managed services over self-hosting, since patching becomes a continuous operational task that customers would rather outsource.
	- **Open-source projects are the most exposed**: volunteer and vendor-funded committers can't scale review the way a company can hire, so the gap between bugs found and bugs fixed may widen most in open source. Long term, that could push more critical open-source software toward vendor-funded maintenance, or toward AI review agents trusted to commit, which Postgres isn't ready to accept.
