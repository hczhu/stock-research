- ## Vibe-Coding Field Notes: Model Familiarity Is Becoming a Platform Moat, and the Content Stack Collapses Into the Model
	- **Source**: User-provided excerpt of build notes from Simon Willison's weblog on his Battle Drones project (links to `simonw.github.io/battledrones`, `github.com/simonw/battledrones`, and an Oct 6 2026 "Scrimshaw Jukebox" post). The post body itself was not supplied, so this extracts the enumerated observations only. Dating: a referenced battle record is stamped 2026-10-14, so the post is on or after that date; filed under the memo-creation date. Related: [[2026-06-05-coding-agents-token-demand-and-enterprise-pmf-willison]], [[2026-09-13-casey-muratori-performance-games-engines-as-ai-preview]].
	- **Thesis**: A single developer shipped a 3D multiplayer game with original art, an adaptive procedural soundtrack, and a suite of debug tools — with no asset files, no server, no engine license, and no app store. Three cost centers that defined interactive software economics (implementation labor, content production, internal tooling) compress toward the token bill at once. The more durable investable idea is narrower: **what a model already knows well is becoming a first-order platform-selection criterion**, which converts training-data presence into distribution and penalizes closed or novel APIs.

- ## Training-Data Gravity Is a New Form of Platform Lock-In
	- The stated reason for choosing the stack is model familiarity, not technical merit: Three.js and Phaser are "excellent platforms to build on **that the current models know inside out**." Capability is being selected for what the weights already contain.
	- This inverts how developer platforms have historically been won. Documentation quality, SDK polish, and developer relations mattered because humans read them. When the agent is the integrator, the question becomes whether the library appeared often enough in the pre-training corpus to be used correctly without lookup.
	- Three consequences that can be tested over time:
		- **Old, open, widely-copied libraries gain** share against newer or proprietary alternatives, because corpus presence accrues with age and public usage. Three.js benefits from a decade of public GitHub code; a closed engine's API does not.
		- **Closed APIs carry a visible tax.** Any vendor whose interface is under-represented in training data must now pay for it — via MCP servers, skills files, or in-context documentation — to retain default placement in agent-written code.
		- **The moat is not permanent but it is sticky**, because agent-generated code feeds back into the public corpus and reinforces whatever the models already preferred.
	- Read-through for engine vendors: the competitive threat to a licensed engine is no longer only a cheaper engine. It is a free, older, worse-documented-for-humans web library that the model writes flawlessly on the first try.

- ## The Delivery Stack Collapses to Static Files
	- Static HTML and JavaScript with WebGL is described as "a fantastic medium for games development." The output is files on a static host — no build service, no runtime, no backend.
	- The game became an installable **Progressive Web App without being asked for**: it ran offline, on a plane, from browser cache, with no explicit install step. Offline-capable distribution arrived as a default property of the platform rather than as a feature someone scoped.
	- **Audio-based multiplayer between static HTML games works** — data transmitted over sound between devices, bypassing networking infrastructure entirely. The author found almost no prior art (Siner by Alon Horesh; ggwave by Georgi Gerganov). Two separate signals here: a transport that needs no server or signaling layer, and evidence that agents will reach for obscure, under-exploited techniques because the search cost of doing so is near zero.
	- | Layer historically paid for | What replaced it here | Who is exposed |
	  |----------------------------------|--------------------------------------------|----------------------------------------------|
	  | Game engine license / royalty | Three.js, free and open source | Licensed engine vendors ([[$U]]) |
	  | App store distribution and billing | PWA installed from browser cache | Store take rates ([[$AAPL]], [[$GOOGL]]) |
	  | Multiplayer servers and signaling | Audio-channel peer transport | Realtime backend and netcode services |
	  | Art and audio asset licensing | Model-generated images; code-generated music | Stock asset marketplaces, music licensing |
	  | Internal debug and dev tooling | Prompted into existence per project | Horizontal developer-tool SaaS |
	- The caveat that keeps this honest: this is one hobby project by an unusually capable developer, not a commercial studio shipping at scale with liveops, anti-cheat, retention tooling, and content cadence. The evidence bears on the **floor cost of a playable 3D multiplayer artifact**, which is now near zero, not on the cost of running a game business.

- ## Content Production Folds Into the Model
	- **Images**: giving the agent an OpenAI API key and telling it to generate images "works really well" — and critically, **it can view the images it has generated and iterate on the prompts**. That closes the loop. Generation without inspection needs a human in every cycle; generation with inspection makes art direction an autonomous subroutine.
	- **3D models**: Opus 5.5 is called "spectacular at 3D modeling using Three.js (and Blender, and no doubt other 3D applications)," with the same reported of GPT-6 Astra. Capability is crossing out of code and into the digital-content-creation tools themselves, which is the read-through that matters for [[$ADBE]] and [[$ADSK]]: the DCC application becomes a backend that an agent drives, not an interface a professional sits in.
	- **Music**: "There are no audio files in this project — the soundtrack is entirely generated through code, varies across different maps, and even gets more intense as the battle heats up." Procedural and state-adaptive, so it is not merely a substitute for a licensed track; it is a thing licensing cannot supply at all. Note the distinction from generative-audio startups: no audio model is involved, so there is no per-asset inference cost and no licensing counterparty.
	- The cross-vendor detail is the sharpest competitive signal in the source: **Claude orchestrating OpenAI's image models**. Whoever holds the agent loop owns the user relationship and treats rival frontier models as callable components. Model quality alone does not capture the customer; the orchestration layer does.

- ## Tools Become Free, and the Specification Becomes the Scarce Input
	- "**Tools are effectively free.**" The author prompted up a radio probe, a model browser, and an agent-vs-agent debug viewer — and Claude Code "built a bunch of tools for itself **that I haven't even explored**." Tooling was produced faster than its owner could audit it.
	- The read-through is unkind to horizontal developer-tool SaaS. When a bespoke internal tool costs one prompt, the buy decision survives only where the product carries something a prompt cannot generate: proprietary data, network effects, compliance attestations, or multi-tenant operational scale. Single-purpose inspectors, viewers, dashboards, and debuggers are the exposed tier.
	- "I still can't get over how well the prompt '**Make it a LOT more fun**' worked." Design judgment responded to a one-line, non-technical instruction. If taste is executable, the bottleneck moves from implementation to specification — knowing what to ask for, and recognizing when the answer is good. That is an argument for the durability of design and product roles and against implementation headcount, inside games and outside it.

- ## Tokens Are the Price of the Capability
	- Claude Code "Ultracode" **burns tokens like there's no tomorrow**, but solved audio-based multiplayer — a genuinely hard problem — **from a single prompt**. The trade is explicit and the author accepts it.
	- The direction matters for inference demand. Rising complexity-per-prompt does not reduce tokens per task; it raises the ceiling on what a user will spend a large token budget attempting. Each capability step unlocks a harder class of problem that costs more to solve, which is consistent with the token-consumption thesis in [[2026-06-05-coding-agents-token-demand-and-enterprise-pmf-willison]] rather than a counterexample to it.
	- Watch whether this generalizes past hobby projects. A developer spending freely on a side project tolerates waste a procurement process will not. The question for the labs is whether enterprise buyers accept "burns tokens like there's no tomorrow" as a line item when the output is production software.

- ## What Still Breaks
	- Determinism is the named failure. For replay and multiplayer, the simulation must be reproducible — and `Math.sin()` / `Math.cos()` **return very slightly different numbers in Chrome versus Safari**, desynchronizing replays. Claude replaced them with custom fixed-point math implementations.
	- Two things follow. First, the agent diagnosed and fixed a genuinely subtle platform-level bug, which is evidence of capability depth rather than surface fluency. Second, this is a bug class that **only appears when the artifact is exercised across real browsers and devices** — it is invisible to unit tests and to the model's own reasoning about its code.
	- As generated code volume rises, the verification surface rises with it. Cross-browser and cross-device test infrastructure, replay/determinism harnesses, and runtime observability get more valuable, not less — the one developer-tooling category the "tools are free" dynamic does not obviously commoditize, because its value comes from owning real device fleets and real user sessions rather than from the code that queries them.
