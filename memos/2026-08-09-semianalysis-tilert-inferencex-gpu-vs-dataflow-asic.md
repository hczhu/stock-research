- ## SemiAnalysis: TileRT InferenceX — can GPU software eat the ultra-low-latency ASIC market?
	- **Source**: SemiAnalysis, *"Ultra-High Interactivity on NVIDIA GPUs? — TileRT InferenceX,"* Bryan Shan, Daniel Nishball, Cam Quilici and three others, August 9, 2026. Benchmarks run on **InferenceX**, SemiAnalysis's open-source vendor-neutral inference benchmark (formerly InferenceMAX), supported by Google Cloud, Azure, Oracle, Meta, vLLM, SGLang, PyTorch, HuggingFace, and labs including OpenAI, MiniMax, Z.ai, Qwen, and Moonshot. **Bias note**: SemiAnalysis collaborated with the TileRT maintainers on the benchmark and sells the TCO and Accelerator models the cost figures rely on.
	- **Thesis**: TileRT is a **compiler and runtime**, not a chip, that reaches ultra-high interactivity on stock 8-GPU B200 nodes by abolishing the kernel as the unit of execution. The investable claim is not the speed record — it is that **a GPU fleet can now provision a "speed tier" in software**, which attacks the dataflow-ASIC value proposition at its economic root (fixed hardware ratios) rather than at its technical root (the SRAM roofline, which software cannot touch). Extends [[2026-05-21-hbm-perf-ratio-cerebras-vs-gpus]] and [[2026-05-20-deepseek-r1-token-throughput-per-gpu-vs-interactivity]].
- ## Cost per million output tokens — the headline comparison
	- All figures GLM-5.1 744B, 8k input / 1k output, SemiAnalysis AI TCO model for capex and opex per chip SKU:
	  | Configuration | Precision | Interactivity | Cost per **million output tokens** | vs TileRT |
	  |----------------------------------------|--------------|-------------------|-------------------------------------|-------------------------------|
	  | **TileRT + MTP on 8-GPU B200** | FP8 | **340 tok/s/user** | **\$13.56** | — |
	  | GB200 NVL72 + MTP, concurrency 5 | FP4 | ~176 tok/s/user | **\$13.40** (at \$1.86/GB200-hour) | **+1% cost for 1.9× interactivity** |
	  | GB300 NVL72 SGLang + MTP (best FP8) | FP8 | 108 tok/s/user | **\$35.00** | **TileRT 61% cheaper at 3.1× interactivity** |
	- **The threshold argument matters as much as the price**: *"Cost per token is only meaningful after a system satisfies the latency target."* At 339+ tok/s/user, the feasible set in the measured GPU results **contains only TileRT** — every conventional configuration is disqualified before price is discussed. The fastest conventional point is 176 tok/s/user; the fastest conventional disaggregated FP8 point is 108.
	- **The most commercially loaded line in the piece** is the comparison to a shipping product: TileRT is *"much more value than Claude Code fast mode, up to 2.5× the interactivity but 2× the price per token."* Read the implication directly — **premium "fast mode" SKUs are priced on willingness-to-pay, roughly 2× for 2.5× speed, while the underlying cost delta for comparable speed can be ~1%.** If that holds, fast-tier gross margins are far above blended inference margins, and the article opens by saying exactly that: premium fast modes are *"potentially yielding higher gross margins."* That is the single most useful takeaway for modelling frontier-lab economics.
	- **One reconciliation problem worth flagging before reusing the +1% headline.** TileRT's numbers are internally consistent: 35.4 output tok/s per B200 at \$13.56/M implies **~\$1.73 per B200-hour**, a sensible rate. The GB200 comparison does not close the same way — **286 total tok/s/GPU at \$1.86/GB200-hour implies ~\$1.81 per million, not \$13.40**; producing \$13.40/M at that hourly rate requires ~**38.6 output tok/s/GPU**, a **7.4× gap** from the quoted 286. The likely explanation is that "total tokens/s/GPU" counts prefill plus decode while the price is per *output* token, but at 8k/1k that is only a ~9× wedge and still does not land exactly. **The published intermediates do not let an outsider verify that both columns are computed on the same basis**, and the entire "+1% cost" claim rests on that.
- ## Performance results, and the trade-off underneath them
	- **Notation**: `8k/1k` and `1k/1k` are the benchmark's **input/output token lengths per request** — ~8,000 prompt tokens with ~1,000 generated, and ~1,000 with ~1,000 (conventionally 1k = 1,024). The two halves stress different resources: **input length drives prefill, which is parallel and compute-bound; output length drives decode, which is sequential, re-reads a growing KV cache, and is memory-bandwidth-bound.** That split is the reason PD disaggregation exists at all.
		- **This explains the spread in the table below**: the same engine on the same hardware reaches **494.2 tok/s/user at 1k/1k but only 340 at 8k/1k**, because an 8× shorter context means an ~8× smaller KV cache and therefore far less HBM traffic per generated token. Interactivity is a decode metric, but input length still sets how much cache each decode step must read.
		- **And it is why these are short-context results.** Both scenarios are single-turn with small prompts; the AgentX successor benchmark has a **median input length of 140k tokens** — roughly 17× the longer case here, with multi-turn accumulation on top. TileRT's advantage is measured on small KV caches, so whether it survives a 140k-token cache is the open question, not a detail.
	- | Scenario | TileRT (FP8, 8-GPU B200) | Best conventional | Speedup |
	  |-------------------------|---------------------------|------------------------------------------|-----------|
	  | 8k/1k interactivity | **340 tok/s/user** | 181.4 (GB300 NVL72, NVFP4+MTP) | **1.9×** |
	  | 8k/1k, same precision | 340 | 113.6 (B300, FP8+MTP) | **3.0×** |
	  | 1k/1k interactivity | **494.2 tok/s/user** | 256.3 (GB200 NVL72, FP4+MTP) | **1.9×** |
	  | 1k/1k, same precision | 494.2 | 136.3 (FP8) | **3.6×** |
	  | GLM-5 FP8 744B, headline | up to **500 tok/s/user** | GB300 NVL72, traditional engines | **~3×** |
	  | End-to-end latency, 1k/1k| — | best prior GLM-5.1 result | **4.5× better** |
	  | Decode tail | **3.01s** | 6.54s (best NVFP4+MTP); **18.18s (MI355X)** | **2.2× / 6.0×** |
	- **Two framing points that make the result more impressive than the raw numbers**: TileRT achieves this on an **8-GPU B200 node, not a 72-GPU NVLink scale-up domain** — *"all that extra trouble to set up the complicated copper backplane in the case of the GB300 NVL72 does not come into play at all in boosting interactivity"* at batch size 1. And **TileRT has no FP4 support yet and is already beating non-TileRT FP4 implementations.**
	- **The cost of the speed is aggregate throughput.** At 8k/1k the GB300 FP4+MTP point at concurrency 12 delivers **~240 total tok/s/GPU at 154 tok/s/user**, while TileRT delivers **160.4 total tok/s/GPU at 340 tok/s/user** — roughly **33% less aggregate work per GPU**. TileRT v0.1.5 serves **one in-flight request per decode node**: *"not just a race car, but more like a private rocket ship with room for just one passenger."*
	- Context for how brutal this curve is generally: InferenceX v2 showed that moving interactivity from ~25 to ~260 tok/s/user cut per-GPU throughput from ~5,900 to ~200 tok/s/GPU — a **~30× throughput reduction for a 10× per-user speedup**.
- ## Why GPUs miss their own roofline — latency, not bandwidth
	- **The roofline the hardware should permit**: an 8-GPU HGX B200 has **64 TB/s** aggregate HBM bandwidth; GLM-5 at NVFP4, batch 1, needs only **~21 GB of active-parameter traffic per token**, implying **up to 3,047 tok/s/user** without speculative decoding. *"In practice GPUs come nowhere close."* Same exercise on HGX H200 (38.4 TB/s, 42 GB/token at MXFP8) implies ~1,000 tok/s/user.
	- **The gap is latency.** Traditional engines launch and synchronize thousands of separate kernels; setup and teardown overhead is invisible at conventional serving speeds but dominates as TPOT approaches sub-millisecond. Each kernel also spills half-finished work to HBM, and at small batch sizes kernels are too small to amortize launch, synchronization, and scheduling overhead.
	- **The structural datapoint, and the one with the widest read-through**: *"although GPU memory bandwidth increases by roughly 2–3× each generation, **memory latency has not improved at all**"* — *"even as HBM prices continually increase."* Bandwidth per GPU went from ~0.7 TB/s (P100, 2016) to ~8 TB/s (GB200/GB300) to ~22 TB/s (VR200, 2026). **Latency is flat across that entire curve.** This is a durable argument that latency-bound decode is a *software and architecture* problem that new HBM generations will not fix — relevant to how much of the memory bill is actually buying performance (see [[2026-08-21-sk-hynix-hbm-history-mr-muf-moat]]).
- ## What TileRT does differently from every other inference framework
	- **The one-line distinction**: *"A CUDA graph optimizes the launching of kernels, while **TileRT abolishes the kernel as the unit of execution**."* CUDA graphs still replay separate kernels, so device-side boundary costs remain and on-chip state is wiped at every boundary.
	- **Persistent Engine Kernel**: the entire decode graph is statically compiled ahead of time into one resident kernel. The host launches once; execution stays resident for the whole decode lifecycle; most runtime orchestration moves to compile time.
	- **Tile-level scheduling with warp and block specialization**: work decomposes into tile-level tasks, different warp groups take asynchronous data movement, tensor computation, and communication overlap. Load → barrier → compute → barrier becomes overlapped at tile granularity, with intermediates flowing through **registers, shared memory, and L2 instead of spilling to global memory**. *"Each CTA becomes a small heterogeneous factory rather than a uniform SIMT worker."*
	- **Specialization extended to whole GPUs** — the concrete example is the sharpest illustration: in GLM-5.1's attention layer, **GPU 0 becomes a dedicated Sparse Indexer** (Top-K selection, sparse index construction, routing) while **GPUs 1–7 run the MLA work** (RMSNorm, GEMM, flash sparse attention, AllReduce). Sparse routing, Top-K, dynamic indexing, long-context attention and MTP are not compute-heavy but depend on global information, so forcing every rank through them adds redundant work and synchronization amplification.
	- **Communication moves inside the tile flow** — broadcasts, reductions, and synchronization execute within it, so an entire attention layer is **one kernel launch**, and execution shifts from compute → sync → compute to a continuously overlapping compute ↔ communication ↔ compute pipeline.
- ## How it composes with the existing framework ecosystem — this is not a vLLM replacement
	- **TileRT does not replace vLLM.** vLLM keeps prefill and the whole serving layer: scheduler, chunked prefill, prefix caching, OpenAI-compatible API, operational tooling. **Only latency-critical decode moves to TileRT.** *"TileRT is engineered to be a single-passenger rocket ship, and vLLM remains the plane, car, bus, and train."*
	- **The architecture is PD disaggregation with two decode pools behind one prefill pool**: latency-critical traffic goes through a **TileRT PD Router** that marks `kv_transfer_params`; general traffic uses vLLM's native disaggregation proxy to a conventional vLLM/SGLang decode pool. Composition happens through **vLLM's MultiConnector API** — the TileRTConnector claims only marked requests and is a no-op otherwise, so **both traffic classes share the same prefill server**. KV cache moves by RDMA one-sided write via **Mooncake Transfer Engine and NIXL**. The router applies back-pressure when a decode node is occupied.
	- **Why this matters commercially**: providers do not pay the TileRT premium on all traffic. A speed tier can be sold as a **routing decision on top of an existing vLLM deployment**, not a separate stack — which is why the deployment cost is low enough for it to spread. TileRT comes from the same maintainer organization as the **TileLang DSL**; it is in production at **Xiaomi (MiMo V2.5 Pro UltraSpeed)** and **Z.ai (GLM-5.1 HighSpeed)**.
- ## GPU versus dataflow ASIC: software approaches the roofline, it cannot raise it
	- **The hardware comparison, as published**:
	  | System | On-chip memory | Memory bandwidth | Peak | Roofline ridge (AI) |
	  |-------------------|--------------------|--------------------------|--------------|----------------------|
	  | **Cerebras WSE-3**| **44 GB on-wafer SRAM** | **21 PB/s** | 125 PF/s | ≈ 6 |
	  | SambaNova SN40L | 520 MB SRAM | ~150 TB/s on-die | 638 TF/s | ≈ 4 |
	  | Groq LPU | 230 MB SRAM | 80 TB/s on-die | 188 TF/s | ≈ 2.4 |
	  | NVIDIA B200 | 192 GB HBM3e | 8 TB/s | FP8 beyond 1,000 TF/s | far off-chart |
		- Cerebras CS-3 is also given as ~900,000 cores.
	- **The decisive sentence, and the honest limit on the whole TileRT thesis**: batch-1 decode runs at arithmetic intensity of ~1–2 FLOP/byte, so it is **bandwidth-bound**, and *"the vertical gap is silicon… what separates them is the intercept: bytes per second."* TileRT moves decode **up toward** the B200 roofline but **cannot cross it** — *"software can approach the HBM roofline, but it cannot raise it."* That is why **Cerebras serves a dense 70B at speeds no eight-GPU node can reach regardless of scheduling.**
	- **The architectural difference in one image**: on a GPU, *"every weight [is] refetched from HBM — every layer, every token."* On dataflow silicon (Cerebras WSE, Groq LPU, SambaNova RDU), **weights live on chip and activations flow through them.**
	- **What TileRT actually is**: software analogues of dataflow ideas — AoT scheduling, persistent execution, specialized workers, communication/compute overlap — *"imposed on a machine that was never specialized designed for it."* It earns its numbers *"by spending enormous compiler effort convincing that machinery to impersonate a spatial pipeline"* through statically expanded persistent kernels, hand-carved warp specialization, and per-model compilation against pinned driver stacks. *"Native dataflow silicon never fights its own substrate."*
- ## The real threat to Cerebras, Groq, and SambaNova is fungibility, not speed
	- **This is the most investable argument in the piece, and it is an economic one.** A GPU pool is **one liquid resource** — good at prefill, good at high-to-medium-batch decode, and now credibly strong at ultra-interactive decode — with capacity moving between roles as **a software scheduler decision that can follow demand hour by hour**. An ASIC fleet is the opposite: **the ratio of speed-tier capacity to everything else is fixed in hardware the day the purchase order is signed**, and changing it means months of physical re-racking and re-cabling.
	- **The asymmetry stated plainly**: *"Guess wrong with GPUs and you rebalance in software. Guess wrong with dedicated silicon and you either strand capital in idle speed machines or turn away the exact premium traffic you bought them for."* And because the split between users wanting ordinary conversational latency and users (increasingly **agents**) paying for extreme-interactivity SLOs keeps shifting, *"a correct guess will only be right for a limited period of time."*
	- **The market has already voted, and the deployment pattern is the tell**: neither Xiaomi nor Z.ai *"procured a new dataflow chip. They carved a speed tier out of the accelerator cluster they already ran."* Conclusion — *"**Good enough on hardware you already own tends to beat architecturally pure on hardware you have to buy**."* This is the same fungibility logic Ben Thompson applies to why buyers choose NVIDIA at all in [[2026-08-21-ben-thompson-ilb-risk-relocation-commodity-logic]].
	- **The reframing to carry**: *"TileRT reframes what most buyers need: **not a speed machine, but a speed tier, provisioned dynamically out of the fleet they were going to own anyway**. Cerebras, Groq, and SambaNova are no longer competing against a clumsy kernel-launcher. They are competing against their own execution model, running on fungible hardware, reallocated by a config file."*
	- **The concession**: this does not kill the top of the speed market. The SRAM roofline is still better, certain model sizes still favor it, and some workloads will pay any price for maximum tokens/s. **The ASIC TAM compresses from "the interactive market" to "the extreme tail of the interactive market."**
- ## Where TileRT is weak — it inherits the ASIC vendors' own worst problem
	- **Static ahead-of-time compilation forces a tiny model catalog**: currently only **GLM-5/5.1 and DeepSeek-V3.2**. MiMo-V2.5-Pro-UltraSpeed came from a co-design partnership and has not been open-sourced. **GLM-5.1 is already a generation behind and deprecated on mainline InferenceX** — the benchmark headline is set on a model nobody will serve for long.
	- Because the model is statically expanded into one resident program, tile shapes, pipeline depth, buffer residency, warp-group splits, collective fusion points, and GPU role assignment are all baked in. **Change the attention mechanism or the routing scheme and much of the schedule is invalidated.** Dependencies are hard-pinned. *"Dataflow chips also face this same issue; good compilers can be notoriously difficult to create."*
	- **The monolithic persistent kernel also breaks the tooling**: conventional per-kernel profiler timelines lose usefulness, making automated feedback loops harder. **TileOps** is the mitigation — a machine-readable per-operator manifest (signature, workloads, roofline model) driving codegen, testing, and benchmarking **against hardware bounds rather than prior implementations**. AI coding agents accelerate tuning inside known templates, but *"novel transformations still require expert judgment."*
	- **The honest read**: TileRT's economic advantage is real but its **generality is not yet demonstrated**. If per-model compiler effort stays high, the speed tier is available only for a handful of models at any moment — which materially narrows how much ASIC TAM it can actually take.
- ## What to watch next
	- **AgentX** — SemiAnalysis is moving TileRT benchmarking off single-turn 8k/1k onto a new agentic coding benchmark replaying **real Claude Code and Codex traces** with long-context multi-turn requests, subagent activity, and dynamic tool-use delays. **Median input length 140k tokens; theoretical median cache-hit-rate roofline 99.2%.** The stated critical question is *"whether TileRT can transfer only the newly introduced context between turns while preserving its ultra-high interactivity advantage."* **This is the test that decides whether the speed tier is real for agents**, which is the segment actually willing to pay for it.
	- **Batch sizes 2, 4, and 8** will be benchmarked to map the throughput–interactivity Pareto frontier and locate where the persistent kernel's latency advantage flattens. If it holds past batch 1, the aggregate-throughput penalty shrinks and the economics improve sharply.
	- **Committed submissions**: NVIDIA has committed verifiable **Vera Rubin** numbers to InferenceX; **Google TPUv7** results are expected soon; **AMD MI455X UALoE72** this year.
	- **A quiet competitive datapoint**: the article refers to frontier labs including OpenAI evaluating *"Cerebras and NVIDIA Groq LPUs,"* and the SemiAnalysis Accelerator Model now tracks quarterly *"NVIDIA LPU30, LPU40, Cerebras WSE-3 and WSE-4 shipments."* **NVIDIA appears to have its own LPU line** — which would mean the ultra-low-latency segment is being attacked by NVIDIA from both directions at once, in software via the GPU fleet and in hardware via dedicated parts.
- ## Glossary
	- **Metrics**
		- **Interactivity** (tok/s/user) — how fast a single user receives tokens; the inverse of TPOT. Decides whether a response feels snappy.
		- **TPOT** — time per output token. Sub-millisecond TPOT is where kernel launch and teardown overhead starts to dominate.
		- **Throughput** (tok/s/GPU) — total tokens produced across all users per GPU. Largely determines cost per token.
		- **TTFT** — time to first token; dominated by prefill. TileRT's is "good but not exceptional."
		- **Decode tail** — time to finish generating after the first token. Where TileRT's advantage concentrates (3.01s vs 6.54s).
		- **8k/1k, 1k/1k** — input/output token lengths per request; see the Notation note above the performance table.
		- **Iso-cost** — comparing configurations at equal cost per token rather than equal speed. The basis of the "+1% cost for 1.9× interactivity" claim.
		- **TCO** — total cost of ownership; the capex-plus-opex model behind every \$/M-token figure here.
	- **Inference phases and serving**
		- **Prefill** — processes the whole input prompt in one parallel pass. **Compute-bound.**
		- **Decode** — generates output tokens one at a time, re-reading a growing KV cache. **Memory-bandwidth-bound.**
		- **PD** — prefill/decode. **PD disaggregation** puts the two phases on separate node pools; the **PD ratio** is how a fleet is split between them, which is a software setting on GPUs and a hardware commitment on ASICs.
		- **KV cache** — stored keys and values for all prior tokens. Grows linearly with context and must be read at every decode step, which is why it is the central bandwidth problem.
		- **MTP** — multi-token prediction; emits several tokens per step to raise effective interactivity. Appears as "+MTP" in benchmark labels.
		- **Speculative decoding** — a cheap draft model proposes tokens that the full model verifies in parallel.
		- **Concurrency** — in-flight requests per node. TileRT v0.1.5 runs at concurrency 1, which is the source of its throughput penalty.
		- **RDMA / Mooncake / NIXL** — the one-sided-write transport and transfer engines that move KV cache from prefill nodes to decode nodes.
	- **GPU execution model**
		- **Kernel** — a GPU program launched from the host. Traditional engines launch thousands sequentially per token.
		- **CUDA graph** — replays a captured graph of kernel launches in one call. Reduces launch cost but **keeps kernel boundaries**, so on-chip state is still wiped at each one.
		- **Persistent Engine Kernel** — TileRT's single resident kernel holding the entire decode graph; the host launches once and execution stays resident.
		- **AoT compilation** — ahead-of-time. The schedule is fixed at compile time, which is exactly why the supported model catalog is small.
		- **Warp / warp specialization** — a warp is a group of threads executing together; specialization assigns different warp groups to data movement, computation, and communication so they overlap.
		- **CTA** — cooperative thread array (a thread block). TileRT turns each into a "heterogeneous factory" rather than a uniform **SIMT** (single instruction, multiple threads) worker.
		- **MLA** — multi-head latent attention, the attention variant in GLM-5.x whose work TileRT splits across GPUs 1–7 while GPU 0 runs the sparse indexer.
	- **Hardware and rooflines**
		- **HBM** — high-bandwidth memory stacked beside the GPU die. Large capacity and high bandwidth, but **latency has been flat for a decade**.
		- **SRAM** — on-chip memory; far faster and far smaller. The basis of dataflow accelerators.
		- **Roofline** — the performance ceiling as a function of arithmetic intensity: a sloped bandwidth-bound region, then a flat compute-bound region.
		- **Arithmetic intensity** — FLOPs performed per byte read. Batch-1 decode sits at ~1–2, deep in the bandwidth-bound region, which is why software cannot raise the ceiling.
		- **Roofline ridge** (ridge point) — the arithmetic intensity where the sloped bandwidth-bound region meets the flat compute-bound region, i.e. **peak compute ÷ peak memory bandwidth**. Below the ridge a workload is bandwidth-bound; above it, compute-bound. It is the "Roofline ridge (AI)" column in the hardware table above — Cerebras WSE-3 ≈ 6, SambaNova SN40L ≈ 4, Groq LPU ≈ 2.4, with B200 far off-chart.
			- **Why the B200's ridge sits so far right**: enormous FP8 compute against 8 TB/s of HBM. Since batch-1 decode runs at an arithmetic intensity of only ~1–2, **every one of these systems is bandwidth-bound at batch 1** — but the GPU is bandwidth-bound by the widest margin, which is the quantitative form of "the vertical gap is silicon." A lower ridge is not a weakness here; it means the machine reaches its compute ceiling at a workload shape that decode actually has.
		- **Dataflow / spatial architecture** — weights stay resident on chip and activations flow through, versus a GPU refetching every weight from HBM every layer, every token.
		- **LPU / WSE / RDU** — Groq's Language Processing Unit, Cerebras's Wafer Scale Engine, SambaNova's Reconfigurable Dataflow Unit.
		- **NVL72** — a 72-GPU NVLink scale-up domain. Notable here because TileRT's results come from a plain 8-GPU node instead.
		- **FP8 / FP4 / NVFP4 / MXFP8** — reduced numeric precisions. Fewer bytes per parameter means less decode bandwidth, which is why FP4 results are normally faster.
	- **Software and benchmarks**
		- **vLLM / SGLang** — the dominant open-source serving engines. Here vLLM keeps prefill plus the whole serving layer, and only latency-critical decode moves to TileRT.
		- **MultiConnector** — the vLLM API that lets the TileRT connector claim only marked requests and no-op on everything else, so both traffic classes share one prefill pool.
		- **TileLang / TileOps** — the DSL built by TileRT's maintainer organization, and the operator-manifest system intended to reduce per-model tuning effort.
		- **InferenceX** — SemiAnalysis's open, vendor-neutral benchmark platform (formerly InferenceMAX). **AgentX** is the agentic successor scenario replaying real Claude Code and Codex traces.
